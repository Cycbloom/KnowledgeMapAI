# P0 阶段：任务队列改造实施计划

本计划旨在将现有的 **数据库轮询 (Polling)** 任务机制改造为基于 **Redis + BullMQ** 的专业消息队列系统，以解决并发冲突和延迟问题。

## 1. 依赖安装
- 在 `api/` 目录下安装核心依赖：
  ```bash
  npm install bullmq
  ```
  *(注：项目已存在 `ioredis`，可直接复用)*

## 2. 核心架构重构

### A. 创建队列服务 (`api/services/queue.ts`)
- **Queue**: 初始化 `taskQueue`，用于生产者（API）提交任务。
- **Worker**: 初始化 `taskWorker`，用于消费者（后台）处理任务。
- **配置**: 复用环境变量 `REDIS_URL`，确保与现有 Redis 连接配置一致。

### B. 改造任务处理器 (`api/jobs/taskProcessor.ts`)
- **移除轮询**: 删除 `processPendingTasks` 方法及其中的循环逻辑。
- **新增单任务处理**: 实现 `processTask(taskId: string)` 方法。
  - 逻辑：根据 ID 从数据库获取任务 -> 执行对应业务逻辑 (`handleGenerateQuestions` 等) -> 更新数据库状态。
  - 保持对数据库的状态更新，确保前端轮询兼容性不受影响。

### C. 改造任务服务 (`api/services/taskService.ts`)
- **生产者集成**: 在 `createTask` 和 `batchProcess` 方法中，当任务插入数据库后，立即调用 `taskQueue.add()` 将任务 ID 推送至 Redis 队列。

### D. 清理服务入口 (`api/server.ts`)
- **移除定时器**: 删除 `setInterval(() => taskProcessor.processPendingTasks(), 5000)` 代码块。
- **启动 Worker**: 在服务器启动时初始化 Queue Worker。

## 3. 验证计划
1.  **环境检查**: 确认 Redis 服务已启动。
2.  **功能测试**:
    - 调用 `POST /api/ai/batch-generate-cards` 创建批量任务。
    - 观察控制台日志，确认任务被 BullMQ Worker **立即捕获**（无 5秒 延迟）。
    - 检查数据库 `tasks` 表，确认状态由 `pending` -> `processing` -> `completed` 正常流转。
3.  **兼容性验证**: 前端页面应能正常显示进度条（通过继续轮询数据库实现）。

## 4. 下一步（预告）
- 本次改造完成后，前端仍通过轮询 API 获取进度。后续（P0-3）将引入 WebSocket/SSE 实现进度的实时推送。
