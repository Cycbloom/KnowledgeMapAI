## 一、路线图总览

### 1.1 Phase 划分

| Phase | 主题 | 功能数 | 核心目标 |
|-------|------|--------|---------|
| Phase 1 | 知识组织基础 | 4 | 构建"双链 + 卡片追溯"基础 |
| Phase 2 | 记忆强化与诊断 | 3 | 提升记忆效率与诊断能力 |
| Phase 3 | 个人管理闭环 | 4 | 构建"学习+工作+习惯"管理闭环 |
| Phase 4 | 输入域扩展 | 6 | 打通外部信息流入通道 |

### 1.2 顺序选择的理由

**推荐顺序：B → D → F → A**

| 顺序 | 理由 |
|------|------|
| Phase 1 (B) 先行 | B 域是组织基础设施，影响 D/F/A 域的关联方式。先做避免返工 |
| Phase 2 (D) 次之 | D 域依赖 B1 双链（卡片↔节点关联），且直接提升学习效果 |
| Phase 3 (F) 再次 | F 域相对独立，但依赖 D 域的学习数据来生成日报/统计 |
| Phase 4 (A) 最后 | A 域内容流入后需要立即用 B 域组织、D 域记忆，依赖前 3 Phase |

### 1.3 与架构优化路线图的关系

本路线图是**功能路线图**，与 [architecture-optimization-roadmap.md](./architecture-optimization-roadmap.md) 互补：

| 维度 | 功能路线图（本文档） | 架构优化路线图 |
|------|---------------------|---------------|
| 关注点 | 新功能交付 | 代码质量/性能/可维护性 |
| 驱动 | 用户需求 | 技术债务 |
| 顺序 | Phase 1-4 | Milestone 1-5 |
| 协调 | 功能开发前先查看架构路线图，避免在待重构模块上叠加新功能 |

## 三、Phase 1：知识组织基础

### 3.1 目标

构建"双链 + 卡片追溯"基础，让知识能反向发现、卡片能追溯节点。

### 3.2 功能清单

| 编号 | 功能 | 性质 | 工作量 | 依赖 |
|------|------|------|--------|------|
| B1 | 双向链接 / 反向链接 | 新建 | 中 | 无 |
| B3 | 双链与图谱边同步 | 整合 | 中 | B1 |
| B6 | Daily Notes / 日记 | 新建 | 中 | B1 |
| D2 | 笔记即卡片（节点级） | 增强 | 大 | B1（关联增强） |
| D7 | 上下文卡片 | 增强 | 小 | D2 |

### 3.3 功能详述

#### B1 双向链接 / 反向链接

- **借鉴竞品**：Obsidian / Logseq
- **核心能力**：
  - 节点内容中输入 `[[节点名]]` 触发引用补全
  - `[[]]` 实时渲染为可点击内部链接
  - 节点详情页新增"反向链接"面板，显示所有引用该节点的节点列表
  - 点击反向链接可跳转到引用位置
- **现有基础**：
  - `markdownParser` 已支持 `[[]]` 解析（仅导入时）
  - `edges` 表 + `relates_to` 关系类型可承载双链
- **新增部分**：
  - 运行时实时解析与渲染
  - 反向链接查询 API
  - 反向链接面板 UI 组件
  - `[[` 触发的节点选择器

#### B3 双链与图谱边同步

- **借鉴竞品**：Obsidian（双链即图谱）+ Heptabase（白板关联）
- **核心能力**：
  - 双链自动生成 `relates_to` 图谱边
  - 图谱边删除时同步移除双链
  - 图谱边添加时可选择是否生成双链文本
- **设计原则**：双链即图谱边，避免两套关联系统

#### B6 Daily Notes / 日记

- **借鉴竞品**：Logseq（日记驱动）
- **核心能力**：
  - 每日自动创建日记页面（可配置时间）
  - 日记支持时间戳条目（`- 10:30 做了xx`）
  - 日记中可 `[[引用]]` 任意节点
  - 日记列表导航（按日期切换）
- **现有基础**：无
- **新增部分**：
  - `daily_notes` 表
  - 日记页面 UI
  - 日记与节点的双链关联

#### D2 笔记即卡片（节点级）

- **借鉴竞品**：RemNote（笔记即卡片）
- **核心能力**：
  - 节点内容可直接"标记为卡片"（正反面分离）
  - 卡片与源节点双向关联（修改卡片可回溯节点）
  - 节点详情页显示"关联卡片"列表
- **现有基础**：`study_cards.knowledge_point_id` 关联已存在
- **新增部分**：
  - 节点→卡片的快速创建入口
  - 卡片↔节点的双向关联 UI
  - 节点内容到卡片正反面的映射规则
- **降级说明**：因 B2 暂缓，D2 为节点级（非段落级），整节点→卡片

#### D7 上下文卡片

- **借鉴竞品**：RemNote（reference backlink）
- **核心能力**：
  - 卡片正面显示"原文出处"标签（节点名 + 图谱名）
  - 点击出处跳转到源节点
  - 复习时可选"查看上下文"展开节点内容
- **现有基础**：卡片已关联 `knowledge_point_id`
- **新增部分**：
  - 卡片正面出处显示
  - 跳转逻辑（`knowledge_point_id` → `graph_nodes` → 图谱定位）

### 3.4 Phase 1 验收标准

- [ ] 节点内容中输入 `[[` 触发引用补全
- [ ] `[[]]` 渲染为可点击链接，点击跳转目标节点
- [ ] 节点详情页显示"反向链接"面板
- [ ] 双链自动生成图谱边，图谱边删除同步移除双链
- [ ] 可创建 Daily Notes，日记中可引用节点
- [ ] 节点可直接生成卡片，卡片显示原文出处
- [ ] 复习时点击出处可跳转源节点
- [ ] `npm run check` + `npm run lint` 全部通过

## 四、Phase 2：记忆强化与诊断

### 4.1 目标

在 Phase 1 卡片基础上提升记忆效率与诊断能力。

### 4.2 功能清单

| 编号 | 功能 | 性质 | 工作量 | 依赖 |
|------|------|------|--------|------|
| D8 | 跨图谱混合复习 | 新建 | 中 | D2 |
| D4 | 错题本 | 新建 | 中 | 无 |
| D5 | 薄弱点诊断+强化 | 新建 | 中 | D4 |

### 4.3 功能详述

#### D8 跨图谱混合复习

- **借鉴竞品**：Anki（全局复习队列）
- **核心能力**：
  - 全局复习队列，跨所有图谱聚合到期卡片
  - 智能混合策略（按遗忘曲线优先级 + 科目权重）
  - 可配置每日复习上限
  - 复习进度可视化（今日已复习/待复习）
- **现有基础**：`study_cards` 全局可见，FSRS 调度已存在
- **新增部分**：
  - 全局复习队列 API
  - 混合策略算法
  - 全局复习页面（区别于单图谱复习）

#### D4 错题本

- **借鉴竞品**：Anki（filtered deck）
- **核心能力**：
  - 复习失败（rating=Again）的卡片自动进入错题本
  - 错题本支持独立强化复习模式（连续答对 N 次后移出）
  - 错题本可手动添加/移除卡片
  - 错题本统计（错误次数、最近错误时间）
- **现有基础**：`practice_results.correct=false` 数据可聚合
- **新增部分**：
  - 错题本视图（基于 `practice_results` 聚合）
  - 独立复习模式
  - 错题本 API

#### D5 薄弱点诊断+强化

- **借鉴竞品**：Anki 统计中心
- **核心能力**：
  - 基于复习数据多维诊断（错误率、稳定度、遗忘速度）
  - 识别薄弱节点（非卡片级，上升到节点级）
  - 推荐针对性强化卡片
  - 薄弱点可视化画像（按图谱/科目/标签维度）
- **现有基础**：`dashboard.blindSpots`（低稳定度卡片 Top10）
- **新增部分**：
  - 多维诊断算法
  - 节点级薄弱点聚合
  - 强化推荐逻辑
  - 薄弱点画像 UI

### 4.4 Phase 2 验收标准

- [ ] 可进入"全局复习"模式，跨图谱混合复习到期卡片
- [ ] 复习失败的卡片自动进入错题本
- [ ] 错题本可独立复习，连续答对后移出
- [ ] 可查看薄弱点诊断报告（节点级）
- [ ] 薄弱点报告可推荐针对性强化卡片
- [ ] `npm run check` + `npm run lint` 全部通过

## 五、Phase 3：个人管理闭环

### 5.1 目标

构建"学习+工作+习惯"的个人管理闭环，与学习数据联动激励。

### 5.2 功能清单

| 编号 | 功能 | 性质 | 工作量 | 依赖 |
|------|------|------|--------|------|
| F3 | 日报/周报自动生成 | 新建 | 中 | D 域学习数据 |
| F7 | 全维度时间统计 | 增强 | 中 | F3 + 现有统计 |
| F6 | 习惯追踪看板 | 新建 | 中 | 无 |
| F4 | 项目空间+资料归档 | 新建 | 中 | 无（复用 graph） |

### 5.3 功能详述

#### F3 日报/周报自动生成

- **借鉴竞品**：Notion（日报模板）+ Logseq（日记驱动）
- **核心能力**：
  - 日报：自动汇总当日完成任务、学习卡片、专注时长、活动记录
  - 周报：自动汇总本周数据，含趋势对比
  - 报告可编辑补充（手动添加反思、心得）
  - 报告归档可查
- **现有基础**：
  - `WeeklyReport` / `MonthlyReport` 组件（专注维度）
  - `task_reviews` 表（review_type='daily'，手写反思）
  - 各类统计 API
- **新增部分**：
  - 跨维度数据聚合 service
  - 日报/周报页面
  - 自动生成 + 可编辑 UI

#### F7 全维度时间统计

- **借鉴竞品**：Notion（多视图）+ Heptabase（可视化）
- **核心能力**：
  - 按活动类型（学习/工作/专注/习惯）的时间投入统计
  - 按项目/标签维度的时间分布
  - 多视图切换（日/周/月/项目）
  - 图表可视化（柱状图/饼图/热力图）
- **现有基础**：`/statistics`、`/dashboard`、`/scheduler/analytics` 等分散 API
- **新增部分**：
  - 统一仪表盘页面
  - 跨维度聚合查询
  - 多视图组件

#### F6 习惯追踪看板

- **借鉴竞品**：Streaks + Notion 习惯模板
- **核心能力**：
  - 习惯定义（每日/每周，目标次数）
  - 打卡机制（手动/基于任务自动完成）
  - 连续天数 + 完成率可视化
  - 习惯看板（日历视图）
- **现有基础**：
  - `periodic_tasks` 表（daily/weekly/monthly 目标）
  - `user_focus_stats` 的 streak 字段
- **新增部分**：
  - `habits` 表（习惯定义）+ `habit_checkins` 表（打卡记录）
  - 习惯看板 UI
  - 与 streak 机制整合

#### F4 项目空间+资料归档

- **借鉴竞品**：Notion（项目空间）+ Heptabase（卡片归档）
- **核心能力**：
  - **复用 graph 作为项目载体**，通过 `properties` 字段标记 `type: 'project'`
  - 项目空间视图：聚合该 graph 下的任务、资料、笔记
  - 项目归档：项目结束后归档可查，不显示在活跃列表
  - 项目切换器
- **设计原则**：复用 graph，零概念增量
- **新增部分**：
  - graph 类型区分（学习图谱 vs 项目空间）
  - 项目空间聚合视图
  - 归档机制

### 5.4 Phase 3 验收标准

- [ ] 可查看自动生成的日报/周报，含跨维度数据
- [ ] 日报可手动编辑补充反思
- [ ] 可查看全维度时间统计仪表盘
- [ ] 可定义习惯并打卡
- [ ] 习惯看板显示连续天数与完成率
- [ ] 可将 graph 标记为"项目空间"
- [ ] 项目空间可聚合任务、资料、笔记
- [ ] 项目可归档
- [ ] `npm run check` + `npm run lint` 全部通过

## 六、Phase 4：输入域扩展

### 6.1 目标

打通外部信息流入通道，实现"输入 → 组织 → 记忆"完整闭环。

### 6.2 功能清单

| 编号 | 功能 | 性质 | 工作量 | 依赖 | 推荐顺序 |
|------|------|------|--------|------|---------|
| A1 | 统一收件箱 | 新建 | 大 | 无 | 1 |
| A8 | Newsletter/RSS 订阅 | 新建 | 中 | A1 | 2 |
| A3 | PDF/网页高亮批注 | 新建 | 大 | A1 | 3 |
| A4 | 视频字幕+时间戳笔记 | 新建 | 中 | A1 | 4 |
| A5 | 播客订阅+转写 | 增强 | 中 | A1 | 5 |
| A2 | 浏览器剪藏插件 | 新建 | 极大 | A1 | 6 |

### 6.3 功能详述

#### A1 统一收件箱

- **借鉴竞品**：Readwise Reader
- **核心能力**：
  - 统一收件箱页面，聚合所有来源的待处理内容
  - 处理流程：待读 → 标注 → 转化为节点 / 归档
  - 支持手动添加（粘贴链接/文本）
  - 收件箱项可标记优先级
- **现有基础**：无
- **新增部分**：
  - `inbox_items` 表
  - 收件箱页面
  - 处理流程 UI

#### A8 Newsletter/RSS 订阅

- **借鉴竞品**：Readwise Reader
- **核心能力**：
  - 邮箱绑定，Newsletter 自动入库收件箱
  - RSS 源订阅管理
  - 定时拉取新内容
- **现有基础**：无
- **新增部分**：
  - RSS 解析与定时拉取
  - 邮箱接收机制（需要邮件服务）

#### A3 PDF/网页高亮批注

- **借鉴竞品**：Readwise Reader
- **核心能力**：
  - 内置 PDF/网页阅读器
  - 高亮批注（多色分类）
  - 高亮自动转为收件箱项 / 卡片素材
  - 高亮可跳转回原文位置
- **现有基础**：无
- **新增部分**：
  - 阅读器组件
  - 高亮提取与存储
  - 高亮→卡片转化

#### A4 视频字幕+时间戳笔记

- **借鉴竞品**：Readwise Reader（YouTube 高亮）
- **核心能力**：
  - B 站/YouTube 视频字幕抓取
  - 时间戳笔记（点击跳转视频时刻）
  - 笔记可转化为节点
- **现有基础**：无
- **新增部分**：
  - 字幕抓取服务
  - 时间戳笔记组件
  - 视频播放器集成

#### A5 播客订阅+转写

- **借鉴竞品**：Readwise Reader（播客支持）
- **核心能力**：
  - 播客订阅源管理
  - 自动下载新剧集
  - STT 转写（复用现有 qwen3-asr-flash）
  - 转写文本关联节点
- **现有基础**：STT 能力已有
- **新增部分**：
  - 播客订阅管理
  - 下载调度
  - 转写文本→节点关联

#### A2 浏览器剪藏插件

- **借鉴竞品**：Cubox / Readwise Web Clipper
- **核心能力**：
  - 独立 Chrome/Edge 扩展
  - 多模式剪藏：全文/选中/截图/PDF
  - 与桌面应用通信（原生消息或云端中转）
  - 剪藏内容入库收件箱
- **现有基础**：无
- **新增部分**：
  - 独立扩展项目（Manifest V3）
  - 通信机制
  - 多模式剪藏逻辑
- **特殊性**：工作量极大，独立项目，需单独构建/发布

### 6.4 Phase 4 验收标准

- [ ] 收件箱可聚合多来源内容，可处理（转化/归档）

## 七、风险与注意事项

### 7.1 技术风险

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| B1 双链实时解析性能 | 节点内容多时解析卡顿 | 使用 Web Worker 异步解析，缓存解析结果 |
| D8 混合复习调度复杂度 | 全局队列性能瓶颈 | 复用 FSRS 调度，批量查询优化（参考架构路线图 OPT-05） |
| A2 浏览器扩展通信 | 扩展与桌面应用通信不稳定 | 优先用云端中转，原生消息作为备选 |
| A3 PDF 高亮渲染 | PDF.js 高亮精度与性能 | 参考 Readwise Reader 实现，分页加载 |
| F3 日报数据聚合 | 跨维度聚合查询慢 | 复用缓存机制（`getOrSet`），预聚合关键指标 |

### 7.2 架构协调风险

| 风险 | 缓解措施 |
|------|---------|
| Phase 1 B1 在 `graphService.ts`（1722 行）上叠加新功能 | 开发前查看架构路线图 OPT-02，可先拆分 `graphService` 再加双链 |
| Phase 4 A1 可能与现有 `knowledge_points` 模型冲突 | 设计时明确收件箱项与 knowledge_points 的转化关系，不混淆 |
| Phase 3 F4 复用 graph 可能与学习图谱混淆 | 通过 `properties.type` 严格区分，UI 上区分入口 |

### 7.3 范围控制风险

| 风险 | 缓解措施 |
|------|---------|
| Phase 4 A2 浏览器扩展工作量极大 | 放在 Phase 4 最后，前 5 项完成后评估是否调整 |
| B2 块级引用未来需求 | 当前 B1 节点级双链设计时预留块级扩展空间（如 `block_id` 字段设计） |
| 新功能引入新循环依赖 | 遵循项目分层规则，新服务不反向依赖上层 |
